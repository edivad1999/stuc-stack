# Maintain a verification skill

A feature map rots the moment the app changes. This skill is the upkeep loop for a skill generated by `/create-verification-skill` (project-local `.cursor/skills/verify-*/` with a `features/` map). The unit of rigor is the feature, not every sentence.

Live Drive on Android **must** follow **android-verify** and the generated skill's Launch/Doctor. Do not invent a `check.sh`. Do not claim coverage you did not run. (P18)

## Outcomes

Pick one, and say which:

- **clean** — every feature got source and live coverage; nothing worth shipping. No branch, no PR.
- **changed** — one PR ships proven doc, harness, or map corrections.
- **blocked** — coverage could not finish or a proven fix could not ship safely. Say exactly what blocked it.

## Edit scope

Only edit the verification skill's own directory (`SKILL.md`, `features/`, helpers it owns). Never edit product code: a behavior the map describes that the app no longer does is either doc drift (fix the map) or a product regression (report it, don't paper over it).

## Pass

0. **Locate the target.** Find `verify-*` with launch/drive sections and a feature map. Several → ask which; none → stop and point at `/create-verification-skill`.

1. **Index hygiene.** Read `features/README.md` and glob siblings. Fix missing, extra, duplicate, or dead entries. Sweep order in the README must stay runnable top to bottom, `multi-surface-journeys.md` last.

2. **Source wave.** One read-only subagent per feature file, launched concurrently. Each explains how the user-facing feature works from source, flags likely doc drift with citations, and returns one concise live recipe using **android-verify** commands. Children never drive the app and never edit files. Return: feature summary / source entry points / likely drift or none / one recipe.

3. **Reconcile.** Every feature file has a returned summary. Merge overlapping recipes into as few app states as practical. Spot-check cited drift. Sweep recent churn for user-facing screens missing from the map — require a concrete source path before calling one missing. Copy the last similar screen; do not invent a new Compose architecture per file. (P8)

4. **Live pass.** Required even when source looks clean. The coordinator owns all driving. Follow the verification skill's Launch (assemble → `android describe` / `run` on **one serial this run started**). Exercise every feature at least once. Hold three invariants: (1) doctor before first drive, after any failed drive, and on each fresh emulator session; (2) evidence captured so far survives every cleanup; (3) nothing a drive started outlives that drive — stop emulators this run started, keep artifacts. A doctor failure caused by skill drift is drift: fix under edit scope and retry once. A feature that can't be reached is `verified-unreachable` only with the concrete prerequisite and the route attempted. Any harness fix from triage gets re-driven live before it ships. Final teardown after the last drive; evidence stays.

   If `android` is missing or this host cannot Drive a device, outcome is **blocked** with that reason. `android -V` alone is not a live pass.

5. **Triage.** Wrong user-POV description → doc drift, fix it. Working behavior the harness can't drive → harness gap, fix it (still no Node `check.sh`; call `android` / Gradle). App behavior actually broken → product gap; record it; keep it out of this PR.

6. **Ship or stop.** For changed: one PR of proven corrections, re-read every changed file first. For clean or blocked: no PR, report coverage honestly.

Keep concise run notes in a scratch location; don't commit them.
